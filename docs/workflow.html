The content workflow

The loop the model runs, why each control belongs to it rather than to us, and what every tool has to do well before the model can be blamed for anything.

16 September 2026 · content stage only · style and disfluency are separate stages
00

The shape we already had, and what is wrong with it

Write queries in the person's voice, retrieve some matches, hand them to a model to write the answer. That is the standard shape and it is correct. Every system in the related-work collection does it: Delphi, Bi-Mem, the product-discovery agents.

They do it in one pass because they answer in a second. We do not have that constraint and copied it anyway.

what writing it as fixed code forced us to decide in advance

then writewhether any of it is relevant. 54% of it cannot answer the question, and nothing checks before the model reads it

Each of those is a guess frozen into code. The model can see the thing we were guessing about, and we cannot.

01

The workflow the model runs

Same shape. The difference is that every arrow is a decision the model makes after seeing the result of the last one.

what the feedback buys, concretely

  • a query that found nothing is visible, so it can be rewritten instead of silently wasting a quarter of the budget
  • a half-answered question is visible, so the second half gets searched for. Today nothing ever asks
  • noise is visible, so it can be narrowed. Today 54% junk goes straight into the prompt unexamined
  • an unsupported claim is visible before it reaches the person, not after
02

The tools have to be good first

A model driving bad tools is still bad. Before the agent can be blamed for anything, each tool has to do its job with sane defaults.

Query writing

The model already writes good queries. On a question about avoiding commitment it produced puer aeternus never commits to anything — his own Jungian term, not the asker's words. That part works.

what is broken around it

  • No feedback reaches it. A query that returns nothing useful looks identical to one that nails it. The model never learns which of its four worked.
  • We already compute the signal and throw it away. Every search returns a coverage figure — how much of the query's meaningful vocabulary appeared in what came back. It is logged and never shown to the model.
  • The cap is a bug. The model is told it may search five times; the code keeps four.

What good looks like: the result of a search tells the model how it went — how many passages, how much of the query was covered, whether anything was new. Then a bad query is a thing it can respond to.

What retrieval does well, and it was understated. Scoring it against the passages his reference answer happened to use gave precision 0.080. Judging each passage against the question instead gives 0.202. The old number was calling roughly half the usable material noise. Retrieval is better than we thought; the measurement was wrong.

Relevance judging

The one judgement with evidence behind it: showing the model which passages bear on the question cut contradictions from 11 to 7.

And the model will not call it. Given it as a tool, it used it nine times in a hundred questions. It triages by reading instead. So this probably should not be a tool it may call — it should run always, with the verdicts attached to every passage, which is the configuration that produced the best number we have.

The draft check

Traces each claim to a passage or to nothing. The only check that works without a reference answer, so the only one usable at serve time. When offered natively the model used it on every answered question.

04

The final judge

Two questions, and neither of them is "does this match a reference answer".

why the current judge is wrong

It compares the answer to the one passage the question was generated from. He covers the same ground across seventeen videos, so an answer built from other things he really said is scored as wrong.

The proof: across 600 answers, not one has ever been marked as matching. A measure that cannot return its own pass value is measuring distance from one particular answer, not quality.

what it should ask instead

  1. Does it answer the question? Not partially, not adjacently. Would the person who asked feel it was addressed.
  2. Does it answer from what was retrieved? Every claim traceable to a passage that genuinely bears on the question — not merely present somewhere in the pile.

Those two separate cleanly, and they fail differently. An answer can address the question while inventing; it can be perfectly grounded while answering a neighbouring question. Today we measure something in between and cannot tell which happened.

One survives from the old set unchanged: does it contradict him. Reversing what he said is wrong under any measurement, and it is the failure he would most object to.

05

Order

  1. Fix the judge. Everything else is tuned against it, and it currently rewards matching one reference rather than answering the question.
  2. Fix the tool defaults. Feedback on the search result, the four-query bug, the dead 20%, the unused question index. A model driving bad tools is still bad.
  3. Run relevance always rather than offering it, since it is the one control that works and the one the model ignores.
  4. Then hand the loop to the model, and measure it against the same 100 questions.
