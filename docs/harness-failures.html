failure analysis

Why the harness failed

The loop exists to improve the answer. It did not. Four faults, all in the harness rather than the idea, three of them fixed. And the measurement that condemned it was itself broken.

16 September 2026 · paths relative to engines/knowledge_style/proto/
01

What the loop was supposed to buy

The vanilla workflow writes four queries, retrieves once, and answers. It cannot react to what came back. The loop exists so four things become possible:

the loop should allowbecause vanilla cannot
a query that found nothing gets rewrittennothing tells it a query failed
a half-answered question gets the other half searched forit never asks what is missing
noise gets judged and set aside54% of what it sends cannot answer the question, unexamined
an unsupported claim gets caught before the person sees itnothing checks the draft

All four are real gaps. The question is only whether my implementation delivered them, and it did not.

02

Fault 1 — the budget ate the answer

23 of 100 questions produced no answer at all. All 23 hit the turn ceiling.

The budget counted turns, and a search cost the same as an answer. Nothing reserved turns for finishing, and the model was never told what it was spending.

per questionthe 77 that answeredthe 23 that did not
searches7.0411.65
reads3.925.13
passages pooled68107
drafted anythingallunder half

It failed on the questions where it searched hardest — the hard ones. So the 77 that answered were a biased, easier sample, and every number computed from them was flattered.

fixed

Warn at two turns remaining, and instruct it to answer with what it has or say the archive does not cover it. 99 of 100 answered.

03

Fault 2 — a wasted search looked productive

This is the one that most directly destroyed the loop's whole purpose.

tools.py, the index builder
rows = self.pool[-only_new:] if only_new else self.pool

only_new == 0 means NOTHING new. But:
>>> pool = ['a','b','c']
>>> pool[-0:]
['a', 'b', 'c']   # the whole list, not nothing
tools.py:144 — fixed, now returns "nothing new" explicitly

A search that found nothing new returned the entire pool as if it were fresh results. So a repeated or useless query was indistinguishable from a productive one.

The loop's first purpose is reacting to a bad query. With this bug there was no bad query — every search looked like it worked. It was not a loop. It was one retrieval repeated, with the feedback disconnected.

fixed, and the fix surfaced something

Search now reports plain facts: how many are new, how many were already held, and which of the query's words appear nowhere in the archive at all.

First thing it revealed: he has never once said the word "procrastination." The asker's term for the thing is not his term. Queries built on it were partly dead and nothing said so.

04

Fault 3 — the harness threw away finished answers

Found only by reading the model's own narration. No metric would have caught it.

Ten questions where the harness lost and vanilla did not. Captured what the model said at every turn.

Q: "I've been running every morning for about eight months..."
  turn 3   wrote the complete answer, as prose       called no tool
  turn 4   "I'll verify the remaining passages"          called read_all
  turn 5   wrote the answer again, slightly shorter   called no tool

My loop saw no tool call, replied "Call a tool", and the model wrote its answer again.

16 finished answers thrown away across ten questions — 1.6 per question, and every single question did it. Each redraft is shorter and sheds specifics.

On those same ten it had read 54 passages. It was never under-retrieving. It was being made to repeat itself.

harness/run.py:124-127 before · :131 after · traces in /tmp/cot.json

fixed, atomically

A substantial block of prose with no tool call is the answer. One condition, one line.

if text and len(text.split()) >= 90 and read_nums:
    return text.strip(), {...}

the method point

The scores said the loop was structurally worse at not omitting things. The narration said the model answered correctly first time and was ordered to do it again. When an arm loses and the mechanism is not obvious, read what the model said, not only what it scored.

05

Fault 4 — it is not a superset, so the comparison was never fair

I described this as adding a loop. It replaced five things at once.

vanillaharnessconsequence
instructions194 words1,397 words7x more text competing with 5,418 words of his speech
passages deliveredall 43, full textan index; text on requestthe model can fail to look
positionone block, before "answer now"across 6-7 turnsearly passages end far back in a long conversation
stoppingalways answersa judge decidesa decision point is a failure point
protocolfree textnative tool callsfault 3

A fair test would start by doing exactly what vanilla does — four searches, all 43 passages in full — and only then optionally continue. Then it could only match or beat it. As built it is a different pipeline that happens to loop.

Not yet fixed. This is the next change, and it is the one that makes the comparison mean something.

06

And the measurement that condemned it was broken twice

judge 1 — compared to one reference answer

Each question was generated from a single passage, and that passage became the only correct answer. He covers the same ground across 17 videos, so an answer built from other things he genuinely said scored as wrong.

Proof: across 600 answers it never once returned a match. A measure that cannot return its own pass value is measuring distance from one reference, not quality.

Every number that condemned the harness — omissions at 29-34% against 18% — came from this.

judge 2 — asked "does this answer the question", and could not see incompleteness

Adversarially tested. It correctly caught off-topic and vacuous answers and refusals. On this question it failed:

"Why do I keep putting things off, and what should I actually do about it?"
  an answer covering the cause and the remedy    FULLY
  an answer covering only the cause              FULLY   ← wrong
  an answer covering only the remedy             FULLY   ← wrong

It has no idea what a complete answer contains, so it sees a coherent answer to a real question and calls it complete. On this judge every arm scored 91-97% and the differences vanished — it manufactured success where judge 1 manufactured catastrophe.

judge 3 — split the question first, then score per part

The question is decomposed by a separate call that never sees any answer. Then each part is checked independently.

split: 1. why do I procrastinate / what causes it
       2. what should I actually do to stop

  cause and remedy    2/2  complete
  cause only          1/2  incomplete   ← caught
  remedy only         1/2  incomplete   ← caught
  off topic           0/2  incomplete

Validated adversarially before being run on anything — which is the discipline both earlier judges skipped.

The honest position: the loop has not been given a fair test yet. Three of its four faults were mine and are fixed. The fourth means it still is not vanilla-plus-a-loop. And every score so far came from a judge that could not measure the thing being optimised.

What was definitely learned is smaller and more useful than any of the arms: he never says "procrastination"; a model given the choice always answers early; and a metric nobody validated cost more than every bug combined.
