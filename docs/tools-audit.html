tool audit

Are the tools good enough?

Tool by tool: what is wrong, and what piece of feedback would let the model fix it itself. A model driving bad tools is still bad.

16 September 2026 · measured on 100 questions, 154 queries

One fault, six times over

Every tool works. None of them says how well it worked.

They return content and withhold the one thing that would let the caller react: whether the call succeeded. A search that found nothing looks exactly like a search that found the answer. That is why feedback is the fix rather than better defaults — the defaults are mostly fine, the silence is not.

What that lets the model do, none of which it can do now:

  • rewrite a dud query — it now knows which words drew a blank, so it can try his term instead of the asker's
  • stop re-searching the same ground — "7 you already had" tells it the query was redundant
  • judge the strength of what it got — three strong hits reads differently from fifteen weak ones
  • ignore the padding rather than treating a score of zero as a passage

Every number in that block is already computed. The coverage figure exists in the code and is thrown away. This is plumbing, not research.

Defaults to fix regardless of feedback: drop the zero-score padding, raise the cutoff or return a deeper list so rank 7–12 is reachable, remove the four-query cap, and index the generated questions alongside the passages.

readfine

Returns the full text of the numbers you name, raises on a number that does not exist. The index-not-text split is what makes eight calls affordable instead of two: fifteen passages cost 285 words as an index against 4,509 as text.

One small addition worth having: say how much budget the read consumed. The model has no sense of what it is spending, and the runs that failed had read five times and had nothing left to answer with.

relevanceworks, and is ignored

Judges each pooled passage against the question. The only control we have ever shown to work — forcing its verdicts into the prompt cut contradictions from 11 to 7.

the problem is not the tool

Offered as something the model may call, it used it nine times across a hundred questions. It triages by reading passages itself instead.

So feedback will not fix this, because the model never gets far enough to receive any. The fix is to stop offering it. Run it automatically on every passage entering the pool and attach the verdict to the index line, so the model sees it whether it asked or not — which is exactly the configuration that produced our best number.

That also makes the search feedback sharper: "15 passages, 3 of them answer the question" is a far better signal than a count.

gapuseful, unmeasured

Reads the index and says what the question still needs, as a query. Used 0.62 times per question when available. It produces real second queries — on one question it returned "procrastination root causes — task aversion, fear of failure, perfectionism", which the deployed system has never generated for any question.

what is wrong

  • it reads the index, which is one line per passage. So it is judging what is missing from titles and first lines, not from content. It will miss a gap that is only visible in a passage's body.
  • it does not know what the model has read, so it cannot distinguish "not retrieved" from "retrieved and unused".
  • never measured alone. We do not know if it helps.

Feedback fix: give it the relevance verdicts and what has been read. Then it can say "you have three passages that answer this and nothing on the second half of the question" rather than guessing from first lines.

checkthe best tool here

Traces each claim in a draft to a passage, or to nothing. The only check that works without a reference answer, so the only one usable when a real person is asking. Offered natively, the model used it on every single answered question.

two gaps

  • it does not say what to do. "This claim rests on nothing" is a verdict. The model then has to decide whether to cut it or search for support, with no help.
  • it cannot see relevance. A claim traced to a passage that does not address the question reads as supported. That is precisely how a grounded answer ends up contradicting him.

Feedback fix: pair each unsupported claim with a suggested query — "nothing supports 'willpower is a finite resource'; try searching for it" — and refuse to mark a claim supported when its passage was judged not to answer the question.

the budgetthe direct cause of a quarter of failures

Twelve turns, counted the same whether the model searches or answers. 23 of 100 questions ran out and produced nothing, having spent 11.65 searches and 5.13 reads. More than half never drafted anything.

The model is never told what it is spending. It receives no signal about turns remaining, so it gathers until the harness cuts it off mid-thought. The failures were on the hard questions — exactly where stopping well matters.

feedback fix, attached to every tool result
4 turns left. Drafting and checking need three. Stop searching.

Default fix alongside it: split the budget so gathering cannot consume the whole thing, and encourage parallel searches — it averaged 11.65 searches across 12 turns, so it is issuing them one at a time when a single turn holds several.

the through-line

Five of the six fixes are the same fix: make the tool report how it went, not just what it found. Almost every number needed is already computed somewhere in the code and discarded before the model sees it.

The exception is relevance, where feedback cannot help because the model never calls it. That one stops being a tool and becomes part of what search returns.
