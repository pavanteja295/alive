01

The shape

Three parts: a set of tools, one piece of shared state, and a model that calls them in whatever order it likes until it decides to answer.

02

The one decision that shapes everything else

Search returns an index, not the text.

The deployed system dumps all 43 passages in full, about 13,000 words, and every later call carries all of it. That is why it can only afford two calls.

Sixteen times cheaper to survey. Full text costs a separate read, so the model pays only for what it wants to see properly. That trade is what turns two calls into eight.

03

The six tools

toolwhat it doeswhat it returnscost
searchword matching over the archive, top 6 plus neighboursan index of what was found, appended to the poolfree
readfull text of the numbers you namethe passages themselvesfree
relevancejudges every pooled passage against the questionper passage: supports an answer, part of one, or no help1 call per 12
gapreads the index and asks what is still missinga query it could run next, or NONE1 call
checktakes a draft, traces each claimclaims resting on nothing, and claims resting on passages it judged irrelevant1 call
answerends the loopthe final text—

Why these six and not others

  • relevance is the only signal we have ever shown to work — showing its verdicts cut contradictions from 11 to 7.
  • gap exists because the deployed system has never searched twice, on any question in any run. This makes "what am I missing" a thing it can ask rather than a thing it must notice.
  • check is the only test that works without a reference answer, so it is the only one usable at serve time.

each tool raises rather than returning something plausible

Six measurement bugs in one day were tools failing quietly. So read raises on a number that does not exist, relevance raises if the judge returns verdicts for fewer than half the passages, and check raises if it parses no claims. A tool that half-worked and scored anyway is what cost us most of a day.

04

Two ways of wiring it, and the difference mattered

First attempt: a text protocol

Our model wrapper sent one text prompt and returned text, with nowhere to put a tool schema. So the model was told to emit one action per line and a regular expression scraped it back out.

# what the model was asked to emit
SEARCH: procrastination why we procrastinate
READ: 3,7,11
RELEVANCE:
CHECK: <draft>
ANSWER: <text>

It worked. On one question: 6 actions, 25 seconds, two searches. And it never called relevance or check — it searched, read, and answered. The same behaviour as the deployed system, which has one tool.

Second attempt: native tool calling

Added a second path to the wrapper that passes real tool definitions and handles the model's tool-use blocks. Each tool gets a schema and a description.

# one of the six definitions
{"name": "relevance",
 "description": "Judge every passage found so far against the
   question: does it support an answer, carry part of one, or not
   help at all. Most of what a search returns does not bear on the
   question even when it shares the topic, and this is how you find
   out which is which.",
 "input_schema": {"type": "object", "properties": {}}}

What a turn actually looks like

One question, the native version, traced.

  turn  what it called
   1    search("procrastination why you put things off")
   1    search("analysis paralysis stuck can't start")     ← two at once
   2    read([19, 20, 24, 26, 28, 22, 23, 31])
   2    search("uncertainty reduce prediction error avoid starting")
   3    read([37, 38, 46, 45, 41])
   3    search("why you don't feel like doing it emotional avoidance")
   4    read([53, 55, 58, 4])
   4    search("provisional life waiting for the right moment")
   5    read([63, 64, 35])
   5    search("what to do instead cultivate what you want")
   6    read([69, 68, 70, 11, 73, 72])
   7    search("exhausted tired can't get anything done after work")
   8    read([74, 75, 76, 77])
   9    check(draft)          ← drafts, then checks it
  10    check(draft)          ← revises, checks again
  11    answer(text)

  11 turns, 79s, 78 passages pooled, relevance never called

Note the pattern: it alternates searching and reading, drafts late, checks twice, and never once asks which passages are relevant. It triages by reading them instead.

06

The budget, and how it broke

Run on the 100 questions, 23 of them never produced an answer. All 23 hit the 12-turn ceiling.

It is the mirror image of the deployed system. That one commits after a single search, on every question ever logged. This one never commits. Same underlying fault: nothing in either version tells the model when it has enough. One guesses too early, the other never guesses.

Fixes, none tested

  • warn it: three turns left, you must answer
  • split the budget — say eight turns to gather, four reserved for drafting and checking
  • push parallel searching. It averaged 11.65 searches over 12 turns, so it is mostly issuing them one at a time when a single turn can hold several

read honestly, this is not a win

  • Contradictions at 6.5% against a best of 7.0% is half a point, with no noise floor, on a smaller and easier sample.
  • The 77 are the easy questions. The 23 failures pooled 107 passages against 68, so it failed on the hardest ones. Recovering them would most likely push both numbers up.
  • Grounding got worse and it takes nearly twice as long.

the index-not-text decision—yes. Sixteen times cheaper to survey; it is what makes eight calls affordable

the 12-turn budget—no. It is the direct cause of the 23 failures

the awkward finding

The one tool we have evidence for is the one the model will not use. Showing relevance verdicts cut contradictions from 11 to 7 when the harness forced them into the prompt. Given the same verdicts as a tool it could call, it calls it nine times in a hundred.

Which suggests the answer is not to offer it. It is to run it always and put the verdicts in front of the model whether it asked or not — the configuration that already produced the best contradiction number we have.
