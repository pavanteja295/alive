Harness Equivalence Ladder

How the deployed answer pipeline was reproduced inside the agentic harness, and what the harness costs once the comparison is fair.

alive / engines / knowledge_style · 16 September 2026 · 100-question set, k=6

The question, answered first

You asked whether the deployed behaviour was hardcoded into the harness or whether the harness keeps its own flow. Neither, and the distinction matters.

What was actually done

The harness does not contain a copy of the deployed prompt. It imports the deployed prompt builder and calls it. Two functions were lifted out of the deployed benchmark and given a single owner; the harness calls those same functions.

answer_bench.py:105  prompt_head()  → who he is, 18 verbatim style exemplars, the 150–250 word instruction

answer_bench.py:122  searches()  → the retrieved passages, rendered exactly as deployed renders them

The deployed path calls them at answer_bench.py:171 and answer_bench.py:246. The harness calls them at harness/ladder.py:192 and harness/ladder.py:353, having imported the module at harness/ladder.py:47.

So equivalence is structural. There is no second copy that can drift. If the deployed prompt changes tomorrow, the harness changes with it.

The flow above that shared context is the harness's own: a tool-calling conversation, a turn budget, a sufficiency judge. What changed is that the harness no longer builds its own version of the input.

Why this was necessary

The first harness was written as a parallel pipeline and then compared to the deployed one. It lost. Nothing could be concluded from that, because it differed in five ways at once, and not one of the five is a loop. Each was an independent reason to lose.

One difference deliberately kept

Levels 1 and 2 cannot close with the deployed system's final line, "You have searched enough. Answer now", because that sentence is false when the model is holding a search tool. They close instead with an instruction to answer now unless a named part of the question has no material — so searching is opt-in rather than the path of least resistance. harness/ladder.py:63

This is the only prompt text the ladder introduces. It is worth stating plainly because it is the one place a reader should be suspicious.

The metrics, stated exactly

Every number on this page comes from one of three judges. They ask different questions, they fail differently, and they must not be merged. The columns in the tables below mean exactly what this section says they mean.

Groundedness — did it invent anything

the question it asks"Mark every factual claim the answer makes. A claim is supported only if an excerpt states it." One line per claim, then a total. answer_bench.py:35
what it returnssupported / (supported + unsupported) — a number between 0 and 1. Deployed scores 0.891.
compared againstEvery passage the model was given. Not a reference answer — the retrieved text itself.
what it cannot seeWhether the retrieval was the right retrieval. An answer grounded in irrelevant passages scores high. It proves nothing was fabricated, and nothing more.

One instrument note that mattered: this judge was truncating its input at 60,000 characters, so it saw 79% of the passages at k=6 but only 25% at k=25. Claims supported by the passages it never saw scored UNSUPPORTED, which made better retrieval read as worse grounding. The cap is gone and an assertion now fails the run if the judge is not shown everything the model saw.

Fidelity — did it reach the points he reaches

the question it asks"REFERENCE is what a person actually said. CANDIDATE is another answer to the same question. Judge CONTENT only." answer_bench.py:52
what it returnsOne verdict per answer:
SAME the same claims
DROPPED he makes a claim it never reaches
ADDED it asserts something he does not
CONTRADICTS it reverses something he says
ELSEWHERE right claim, wrong thing attached
compared againstHis actual transcript answer to that question, pulled from the corpus row the question was generated from.
what it cannot seeWhether the question was answered. This is measured, not asserted — see below.

This is the source of every DROPPED and CONTRADICTS figure on the page, and it is the metric I spent the day ranking arms with. Two properties make that a mistake.

SAME has never been returned once across 600-plus answers. A measure that cannot produce its own pass value is measuring distance from one particular answer, not quality. He answers from one to three passages; the model is handed 41. The modal verdict is ADDED at roughly two thirds, which the metric records without penalising.

And it does not detect incompleteness. Cross-tabulated against the completeness judge on the deployed arm:

fidelity verdictanswers the questionmisses a part
ADDED588
DROPPED210
CONTRADICTS130

All 21 DROPPED answers fully answer the question, and none of the 8 genuinely incomplete answers were flagged DROPPED. The two are near-orthogonal. DROPPED means "did not reproduce his particular emphasis"; real incompleteness hides inside ADDED — answers that say plenty, just not the part that was asked.

CONTRADICTS is the one verdict here that survives unchanged, because reversing what he said is wrong under any measurement.

Completeness — did it answer what was asked

step 1, the splitThe question is broken into the distinct things it asks, in a call that never sees any answer. "Split only where a real answer could cover one and miss the other." judge2.py:26
step 2, per partFor each part separately: "Does the answer address THIS PART? Ignore the rest of the question." One word, YES or NO. judge2.py:43
what it returnscomplete — share of questions where every part is covered
parts covered — share of all parts covered
reported split by 1-part and 2+ part
compared againstThe question itself, decomposed. No reference answer is involved at any point.

The split is computed once and shared across all arms, so arms are scored on the same decomposition rather than on separate ones. On this 100-question set it yields 40 single-part, 54 two-part, 6 three-part.

This is the metric that answers "how well does it answer the question", and it is the one the tables should be read on. Deployed scores 92% complete, 95% of parts covered, 98% on single-part questions and 88% on multi-part.

The judge this replaced, and why

An earlier judge asked the question holistically: "does it answer the question", returning FULLY / PARTLY / ADJACENT / NO / DECLINED. judge.py:22

Adversarially tested, it correctly caught off-topic answers, vacuous answers and refusals. But on a genuine two-part question it gave FULLY to an answer covering only the first part, and also to one covering only the second. It cannot see incompleteness, because it has no idea what a complete answer contains. Its numbers (91–97% FULLY) are unusable and are not quoted on this page.

Decomposing first is what fixed it. The lesson generalises: a judge asked to hold the whole question in mind while scoring will score an impression.

the live weakness in the metric I am now relying on

The completeness judge's split is itself a model call, and it over-splits. A second decomposer, written with deliberately different wording, agrees on whether a question is multi-part in only 57 of 100 cases — the judge calls 60 questions multi-part, the second calls 17.

"Am I just lazy compared to disciplined people?" is two parts to the judge and one to the second reader. Both are defensible.

So the 98%-versus-88% single-to-multi gap, which the whole failure diagnosis rests on, is soft until the split is settled. This is the next thing to fix, ahead of any further harness work.

The parity proof

Before any model call was spent, the two prompt strings were built side by side and compared. They are the same string, 14,996 words:

identical: True     prompt words: 14996     passages shown: 31

Then level 0 was run over all 100 questions and scored on every judge:

armADDEDDROPPEDCONTRADICTSgroundedcomplete2+ part
deployed, k=66621130.89192%88%
level 0, via harness6621130.89192%88%

Not just equal in aggregate. Per question: 100 of 100 byte-identical answers, 100 of 100 identical fidelity verdicts, 100 of 100 identical grounding scores. Generation took zero seconds because every prompt hit the response cache — which is itself the proof, since the cache is keyed on the prompt text.

What level 0 establishes is narrow and worth stating exactly: the harness infrastructure adds no distortion of its own. It reaches parity by having no loop. Any loss above level 0 is now attributable to the loop and to nothing else.

And then the loop did not fire

the central result

At level 1 the model searched 0.00 times across 100 questions. Given the deployed context, the search tool, and explicit permission to use it, it judged what it already had sufficient every single time. Level 1 is therefore level 0 with a tool schema attached — and its one-point gain on completeness is noise, not a loop win.

This reframes every earlier harness run. The old harness searched three or four times per question not because the model decided it needed more, but because it started from nothing and had no choice. The looping was an artefact of the deficit, not evidence of judgement.

Turn budget was also cut from 10 to 6 on the reasoning that a loop which does not fire does not need headroom. harness/ladder.py:54 versus harness/run.py:35

Why the loop lost, in its own words

The harness records the model's narration before each tool call. A diagnostic selects multi-part questions where the loop missed a part and the deployed single call did not — losses to the loop, not hard questions — and puts one call on each with a fixed list of causes, so the output is a distribution rather than anecdotes. harness/why.py

On v3, the worst-performing loop: 60 multi-part questions, 10 lost, 2 won.

causenwhat the narration shows
NOTHING_FOUND5It searched the missed part properly, found nothing, and said so outright
ANSWERED_FINE2The part is addressed; the completeness judge is wrong
NEVER_NOTICED2The narration never raises the missed part at all
NOTICED_DROPPED1It named the part, searched it, then answered without it

The dominant cause is not the loop failing to look. It is the loop looking, finding nothing, and declining. So the follow-up question is whether the deployed answer covered those same parts with real material or by extrapolating. All five were tested against the passages that were actually retrieved:

The ten losses, attributed

verdictnreading
Genuine loop defect52 never noticed the part, 1 noticed and dropped it, 2 searched badly while the material was present
The loop was right3It declined where the deployed system extrapolated and was rewarded for it
The judge was wrong2The part is addressed

Half the apparent gap is not a loop defect. The completeness judge asks whether a part was addressed, not whether it was addressed truthfully, so a confident extrapolation scores above an honest omission. The loop's sufficiency check makes it more likely to notice it has nothing and say so — and that reads as incompleteness.

The instrument fault that changed the ranking

Two of the three faults found today are covered above: fidelity does not detect incompleteness, and the completeness judge's split is contested. The third was a plain bug in the reporting.

The baseline printed under every harness run was the wrong arm

Every harness report printed baseline 18.0% and baseline 11.0%. Those are the k=25 numbers. The harness runs at k=6, where the deployed system scores 21% and 13%. So the harness was compared against an arm it never ran, and its contradiction rate — consistently 8–12% against the deployed 13% — was read as a loss when it was a win. The baseline is now computed from the stored run at the matching k rather than typed in. harness/ladder.py:300

What is not established

  • No noise floor. No arm has been run twice on any judge. The 92% / 93% spread between level 0 and level 1 is one question and supports no ranking.
  • Level 2 has not been run. The sufficiency judge's cost is unmeasured on the fair comparison.
  • No demonstrated loop win. Level 1 matches the deployed system and never uses its tools. The loop has not yet earned its place, and the honest reading is that on this question set, with this retrieval, one call already gets what is available.
  • The decomposition fix is built but untested. Telling the model what the question owes, up front, addresses 3 of the 10 diagnosed losses. It is available at every level so it can also be tested on the deployed single call — where a gain would be a finding about the deployed system rather than about loops. harness/ladder.py:129
